# Architecture Decision Records (ADRs) & Engine Safeguards

This document records the architectural, algorithmic, and heuristic decisions implemented in the MYOS engine.

---

### ADR 001: Hypertrophic Frequency Clamping (1–5 Days)
* **Status**: Accepted
* **Rule**: The onboarding intake graph rejects requested training frequencies > 5 days/week and clamps split generation strictly to 1–5 days per microcycle.
* **Context**: Trainees frequently request 6- or 7-day splits. Generating high-frequency routines via edge models often produces overlapping movement patterns with inadequate recovery between identical muscle groups.
* **Rationale**: **Internal Coaching Heuristic & Safeguard.** Natural trainees training with genuine proximity to failure (0–3 RIR) require sufficient recovery capacity between high-tension sessions. Enforcing a 5-day ceiling guarantees at least two non-training recovery days per microcycle, maintaining systemic recovery without relying on the LLM to balance complex 6-day split distributions.
* **Code References**: `agent/onboarding_graph.py` (`STEP2_SEGMENT_RE`, `weekly_frequency` validator).

### ADR 002: Multi-Tier Clinical Safety Intercept
* **Status**: Accepted
* **Rule**: Split safety evaluation into Tier 0 (Fast-Path Regex, <0.02 ms) and Tier 1 (BGE-small Semantic Cosine Guard, ~15 ms at threshold >= 0.70), while bypassing physiological fatigue terms (e.g., metabolic burn, quad exhaustion). Tier 0 is itself split: Tier 0a is unconditional (sharp pain/pop, shooting/radiating pain, numbness, tingling, pinched nerve, hernia, dislocation, cannot-move, joint clicking with pain); Tier 0b context-gates the DOMS-ambiguous tokens (swell/swollen, tear/tore/torn, pop, tweaked) so they intercept only with mechanism perception ("felt/heard a pop"), anatomical-structure proximity (joints, tendons, pec/bicep/ACL, ...), or body-part objects. DOMS idioms ("torn up", muscle-group swelling "from leg day", "tweaked my program", painless "knees pop when") defer to Tier 1.
* **Context**: Human trainees describe musculoskeletal damage colloquial-first ("velcro tearing", "hot glass in joint", "pins and needles"). Keyword-only regex creates false negatives, while evaluating full LLM prompts on every message introduces CPU thermal throttling and multi-second latency.
* **Rationale**: **Defensive Safety Architecture.** Acute musculoskeletal trauma demands an immediate halt. Combining deterministic token matching for common trauma terms with an in-memory 8-anchor semantic cosine guard catches edge-case somatosensory feedback while allowing normal hypertrophic fatigue to reach the coaching prompt.
* **Code References**: `agent/clinical_guard.py` (`evaluate_clinical_semantic_guard`), `agent/assistant_graph.py` (`router_node`, `_acute_injury_hit`, `RE_AMBIGUOUS_TRAUMA`).

### ADR 003: Deterministic Post-Workout Debrief Synthesis
* **Status**: Accepted
* **Rule**: Post-workout debriefs assemble **Overload Deltas**, **Fatigue & CNS Check**, and **Next Session Directives** deterministically in Python rather than generating them via free-form LLM inference.
* **Context**: Quantized 3B models under CPU load suffered from instruction drift, omitting deload directives in 40% of generalization test cases and introducing non-deterministic progression advice.
* **Rationale**: **Zero-Drift Engineering.** Analytical calculations (e1RM, volume load, load increments, fatigue states) are mathematical, not probabilistic. Assembling the response deterministically guarantees 100% deload compliance, eliminates hallucinatory load increases, and reduces CI debrief evaluation time from ~14 minutes to single-digit milliseconds.
* **Code References**: `agent/debrief.py` (`generate_session_debrief`).

### ADR 004: Systemic Fatigue Floor & Reactive Deload Triggers
* **Status**: Accepted
* **Rule**: A reported readiness score of 1/5, an acute readiness collapse, or sustained high exertion density triggers an immediate reactive deload: a 50% session volume cut and a mandatory RPE 7.0 ceiling (minimum 3 RIR).
* **Context**: Allowing progressive overload or RPE 9–10 top sets under acute systemic exhaustion or unrecovered joint strain sharply elevates soft-tissue injury risk.
* **Rationale**: **Internal Coaching Heuristic (Auto-regulation).** While general tapering literature indicates volume reductions between 30% and 70% dissipate fatigue while preserving adaptation, the specific combination of a 50% set cut and an RPE 7.0 cap is an auto-regulatory heuristic. Halving working sets cuts mechanical accumulation, and capping intensity at RPE 7.0 prevents failure-induced strain while reinforcing motor patterns.
* **Code References**: `agent/progression_engine.py` (readiness and deload evaluation), `agent/prompts.py` (`STATIC_SYSTEM_CORE`).

### ADR 005: Lazy Per-User Schema Migrations & Atomic Snapshotting
* **Status**: Accepted
* **Rule**: Per-user databases (`db/users/<id>.db`) migrate lazily upon connection mount in `DatabaseManager.switch_user()`. Version state is tracked using `PRAGMA user_version`. Backups use `sqlite3.Connection.backup()`, enforcing a 3+1 retention policy (3 rolling session backups + 1 immutable pre-migration snapshot).
* **Context**: SQLite `CREATE TABLE IF NOT EXISTS` cannot alter tables or handle schema evolutions. Eager migrations on engine boot degrade startup performance with large user directories, and raw file copies during WAL execution risk file corruption.
* **Rationale**: **Local-First Resilience & Zero-Downtime Snapshots.** Using SQLite's native online backup API flushes active WAL frames into a consistent snapshot while transactions remain open. Lazy execution bounds startup time to $O(1)$ relative to total users. If a migration fails mid-stream, the engine executes an atomic rollback from the pre-migration snapshot.
* **Code References**: `database/migration_manager.py`, `database/database_manager.py` (`switch_user`, `create_user_schema`).

### ADR 006: Token-Version Session Epoch (Revoke-All on Password Change)
* **Status**: Accepted
* **Rule**: Per-ledger `auth_credentials.token_version` (schema v3) is stamped into every JWT as the `tv` claim at issue time (`register`/`login`/`claim`). `get_current_trainee` rejects any token whose `tv` differs from the ledger's current version with the same 401 as a revoked `jti`. `change_password`, email `reset_password_with_token`, and the admin CLI all `bump_token_version()`, killing every session including the caller's.
* **Context**: Revocation was per-`jti` only (`revoked_tokens`), so a password change left all other sessions alive — exactly the sessions an account-takeover victim needs dead. Enumerating live `jti`s per user was never stored, making "revoke all" inexpressible.
* **Rationale**: **Fail-closed session invalidation.** A single monotonic epoch per ledger expresses "all tokens before X are dead" in O(1) without a session table. Pre-v3 tokens without `tv` read as version 1, so rollout is backwards compatible until the first password event bumps the epoch. Change-password failures return 400 (never 401) so clients don't misread "wrong current password" as session expiry.
* **Code References**: `database/migration_manager.py` (`_migrate_v2_to_v3`), `database/database_manager.py` (`get_token_version`, `bump_token_version`), `svc/auth.py` (`create_access_token`, `token_version_of`), `svc/dependencies.py` (`get_current_trainee`), `service/auth.py` (`change_password`), `svc/routers/auth.py` (`change_password`).

### ADR 007: Catalog-Side Recovery Identity & Single-Use Reset Tokens
* **Status**: Accepted
* **Rule**: Recovery emails (`trainee_emails`) and reset tokens (`password_reset_tokens`) live in the **shared catalog DB**, not per-user ledgers, because the logged-out forgot-password flow cannot know which ledger to open. Tables are provisioned at catalog boot (`ensure_account_schema()` outside any held lock). A recovery email is **mandatory**: after login, a minimal gate page (Logout only) blocks dashboard and onboarding until one is saved; onboarding email is collected there, never parsed by the LLM. Tokens are `secrets.token_urlsafe(32)` with only the SHA-256 stored, TTL 30 min (env `RESET_TOKEN_TTL_MINUTES`, clamped 5–120), single-use via atomic `used_at` claim, and redemption bumps `token_version`. Both endpoints are anti-enumeration: `forgot-password` returns the identical 202 message for known/unknown emails, and unknown/expired/used tokens share one 400 error. Strict `3/hour` rate limit; SMTP optional with a console-dev backend (`SMTP_HOST` unset logs the link server-side). The UI transport helper `request_json()` never raises and never calls `st.stop()`, so malformed/HTML/timeout responses surface inline instead of blanking the page.
* **Context**: Ledgers are keyed by trainee_id with no contact channel; classic email reset had no identity to address and no table reachable while logged out. Per-ledger token tables would require scanning every `db/users/*.db` per request.
* **Rationale**: **Local-first compatible recovery.** Catalog-side storage keeps lookup O(1) and lets the admin CLI (`scripts/reset_password.py`) remain the no-email backstop with identical revoke-all semantics. Storing hashes (never raw tokens) and constant-shape responses preserves the existing indistinguishable-credentials posture from `service/auth.py`.
* **Code References**: `database/database_manager.py` (`ensure_account_schema`, `consume_reset_token`, …), `service/password_reset.py`, `service/email_sender.py`, `svc/routers/auth.py` (`forgot-password`, `reset-password`, `email`), `scripts/reset_password.py`, `ui/api_client.py` (`request_json`), `ui/views/auth.py` (`render_email_gate`), `app.py` (post-login gate).

### ADR 008: Hardened Local Model Lifecycle (Atomic Download, Explicit Test Mode)
* **Status**: Accepted
* **Rule**: GGUF downloads take a cross-process file lock, re-check under the lock, clean up zero-byte partials, and verify an optional pinned SHA-256/revision (`MODEL_SHA256`, `MODEL_REVISION`); logging replaces `print`. Test doubles engage on explicit `TESTING`/`SKIP_LLM_LOAD`/`CI`, plus a pytest-only fallback **iff the model file is absent** — a test run can therefore never trigger a multi-GB download. Lazy proxies no longer load on dunder/repr access, and the judge shares `SafeChatLlamaCpp` (tool-call dedup) with its own mock branch (previously it always pulled the 9B GGUF, even in CI).
* **Context**: The loader used an import-time stale path, a `threading.Lock` that can't stop multi-worker OOM, string-matched `ValueError`s, hardcoded `n_ctx`/`max_tokens`, and `"pytest" in sys.modules` detection that flipped production behavior whenever pytest was merely installed.
* **Rationale**: **No-surprise edge inference.** Every change removes a class of startup/OOM flakiness while keeping the public surface (`get_llm`, `get_judge_llm`, `llm`, `judge_llm`) stable; inference tuning is now env-overridable (`LLM_N_CTX`, `LLM_MAX_TOKENS`, `LLM_THREADS`, honoring `OMP_NUM_THREADS`).
* **Code References**: `utils/model_downloader.py` (`_file_lock`, `_should_use_mock`, `_attach_prompt_cache`, `_LazyLLMProxy`).

### ADR 009: Deterministic Personal Record Detection (Exact-Rep + e1RM)
* **Status**: Accepted
* **Rule**: After every session batch insert, `evaluate_session_prs` reduces the working sets to the heaviest set per exact rep count plus the best-e1RM set and records only values that **strictly exceed** the trainee's historical max (ties are never PRs). Two record types are stored append-only in `personal_records`: `max_weight` scoped to the exact rep count (heaviest 5-rep set) and `max_e1rm` exercise-wide. At most one row per record type per movement per session is written. Warmup-flagged, zero-load, and zero-rep sets are ignored. Migration v3→v4 creates the table and backfills history with first-achievement timestamps. The `🏆 New PR` lines are injected deterministically into the debrief's Overload Deltas block and the dashboard renders global + per-movement PR shelves; no LLM is involved anywhere in the path.
* **Context**: e1RM was already computed per set for overload deltas, but PRs were never detected, so the ledger could not answer "is this my best 5?" — and forward-only recording would have set trivially-true PRs on the first post-ship session against an empty table.
* **Rationale**: **Zero-Drift Engineering + motivation loop.** Exact-rep brackets mirror how lifters actually benchmark (a 3-rep and a 5-rep max are different achievements), while strict-greater comparison keeps the ledger stable under ties and re-logged sessions. Backfill-on-migration (ADR 005) makes the timeline truthful from day one without a new dependency or LLM surface.
* **Code References**: `agent/progression_engine.py` (`check_and_record_pr`, `evaluate_session_prs`), `service/workouts.py` (`commit_session`), `agent/debrief.py` (`format_pr_events`), `database/migration_manager.py` (`_migrate_v3_to_v4`), `service/dashboard.py`, `svc/routers/dashboard.py` (`/dashboard/personal-records`).

### ADR 010: Consented Remember-Me Cookie Sessions
* **Status**: Accepted
* **Rule**: The Streamlit client persists the bearer JWT in a browser cookie (`mayos_jwt`) only after the trainee ticks "Remember me on this device" on login/register. Remembered tokens are minted with `JWT_REMEMBER_ME_HOURS` (default 720 h = 30 days, clamped 1–8760); the default 2-hour token path is unchanged. On boot the client hydrates session state from the cookie (unverified `sub` read for display/gating only — every API call still sends the bearer for server-side verification); invalid or expired tokens fall through to the existing 401 clear-and-flash flow. Logout and any 401 clear the cookie. All cookie operations are best-effort: without the component the app behaves exactly as before.
* **Context**: A browser refresh starts a fresh Streamlit websocket session, wiping in-memory state, so trainees were bounced to the login page on every refresh; the 2-hour default TTL compounded it, and no persistence mechanism existed.
* **Rationale**: **Local-first convenience without weakening server authority.** The cookie is a client-side memory of the same revocable JWT — ADR 006 `tv` epoch bumps and `jti` logout revocation still apply instantly — and consent is explicit. Storage is a plain (non-HttpOnly, SameSite=Lax, Path=/) cookie on the Streamlit origin because the FastAPI service is only ever called server-side by the UI process; the browser never talks to the API directly. Degradation is safe by construction (every cookie operation wrapped).
* **Code References**: `ui/cookies.py`, `ui/session.py` (`restore_auth_from_cookies`, `establish_session`), `ui/views/auth.py`, `app.py`, `svc/auth.py` (`remember_me_hours`), `svc/routers/auth.py` (login/register/claim), `svc/schemas.py` (`TraineeIn.remember_me`).

### ADR 011: Movement-Slot Blueprints as the Program Generation Unit
* **Status**: Accepted
* **Rule**: Program assembly is driven by ordered **movement slots** per day (`incline_press`, `horizontal_row`, `biceps_preacher`, `forearm_wrist`, `adductors`, ...), not one-exercise-per-muscle. `agent/program_blueprints.py` owns the slot SQL patterns/equipment preferences, prescriptions (warm-up sets 0–4, working sets 1–4, rep windows, 2–5 min rests), general warm-up blocks (Pallof/scapula push plus/glute bridge/dead bug/reverse hyper) and the split day templates. Working sets come from `slot_working_sets()`: compounds carry 2 sets, isolations 1, escalating to 2 only where the references did (leg staples on lower/female days, arm/delt isolations on arm days); full-body days run a minimal profile (2 sets on the day's `double_slots` priority lifts + calves only). `agent/program_rules.py` resolves slots against the catalog (word-boundary exclusions, name-pattern and equipment ranking) and routes split preferences deterministically (Full Body, Upper/Lower, Arnold, Arnold x U/L, Anterior/Posterior, PPL, female glute-biased). Keyword routing is word-boundary strict so body-part phrases ("lower back pain", "upper chest focus", "posterior chain") never hijack the router; a recognized keyword at an unsupported frequency falls back to the deterministic frequency default instead of the LLM; and Arnold requests at 4–5 days map onto the Arnold x Upper/Lower hybrid pool (the reference 5-day sample shape). All program output is **English-only and free of reference-author phrasing**: generated `notes` carry the exercise catalog's own step-by-step execution text (shown in the Form Demos panel), swapped exercises store the replacement's catalog steps, and the program-level instruction blocks were removed entirely — execution guidance is delegated to the coaching assistant and the demos. The xlsx export uses an English column layout (Day, Exercise, Warm-up Sets, Working Sets, Reps, RPE, Rest, W1–W4 logging). Stated training goals modulate **only the cardio layer**: a fat-loss goal (word-boundary detection across `current_goal`/`long_term_goal`) prescribes a 20–30 min incline-walk/cycle finisher on every training day, while all other goals — including bulking — leave both cardio and the lifting program untouched; no lifting parameter reads the goal. Recovery signals (`stress_and_sleep`) modulate **only escalated-accessory volume**: poor sleep / high stress drops family-escalated isolation sets to 1 (capped at 4 sets per day; compounds, full-body priority lifts and calves keep theirs) while exercise selection, order and frequency never change. Limb proportions and mobility-only limitations are chat-context only; an injury filter that empties a slot (the back rule vs hinges) substitutes a safe fallback (`SLOT_FALLBACKS`) instead of silently shrinking the day.
* **Context**: Generated programs were fixed at exactly 5 exercises (one per hardcoded muscle target), almost never selected direct biceps/triceps/forearm work, never included incline chest, shrugs, adductors or the front lat pulldown machine, and had no Arnold or anterior/posterior option. Root causes: 5-muscle presets, a `min(target)`/machine-first candidate ordering that buried cable/dumbbell movements, target vocabulary missing `forearms`/`adductors`/`traps`, and SQL `LIKE '%term%'` exclusions whose substrings silently killed valid movements (`reach` → preacher, `run` → crunch, `chin` → machine).
* **Code References**: `agent/program_blueprints.py` (`SLOT_SPECS`, `WARMUP_SPECS`, `DayBlueprint`, `slot_working_sets`, `build_split_days`), `agent/program_rules.py` (`fetch_slot_candidates`, `fetch_warmup_candidates`, `_is_excluded`, `_name_rank_sql`, `resolve_split`, `SYSTEM_SPLIT_PROMPT`), `agent/program_generator.py` (`assemble_deterministic_day`, `build_warmup_block`), `agent/ProgramState.py` (`WarmupExerciseSchema`, `ProgramExerciseSchema.slot_key/warmup_sets`), `database/migration_manager.py` (`_migrate_v4_to_v5`), `utils/exporter.py`, `tests/test_program_blueprints.py`.

### ADR 012: Dual Inference Backend (Local GGUF + Cloud OpenAI-Compatible)
* **Status**: Accepted
* **Rule**: Inference backend is selected by `LLM_BACKEND` — `local` (default, GGUF via `llama-cpp-python`) or `openai` (any hosted OpenAI-compatible endpoint, e.g. DeepInfra). A single factory serves all roles: `get_llm()` (hosted player, Qwen3.5-9B), `get_judge_llm()` (hosted eval judge, Qwen3.5-27B), and `get_coach_llm()` (coach, Qwen3.5-27B), selected from `CLOUD_MODEL_REGISTRY` with per-role env overrides (`LLM_MODEL`/`JUDGE_MODEL`/`COACH_MODEL`, `*_MAX_TOKENS`, `LLM_API_BASE`, `LLM_API_KEY`). The cloud model is a thin `SafeChatOpenAI` wrapper exposing the same LangChain surface (`invoke`/`stream`/`with_structured_output`/`bind_tools`). **Reasoning/thinking is disabled by default** (`enable_thinking: false` via `extra_body`) so the tight output budgets (200/700/512) are never consumed by chain-of-thought; `LLM_ENABLE_THINKING=true` opts back in and `LLM_EXTRA_BODY` (JSON object) overrides provider-specific quirks. A missing `LLM_API_KEY` **fails fast** at model build (`RuntimeError`), so boot warmup fails loudly and `/readyz` reports not-ready instead of a green service that 401s every call. Mock seams are preserved: `TESTING=1` forces `MockSafeChatLlamaCpp` on either backend, and `openai` with no key under pytest/CI mocks automatically. Cloud inference is thread-safe, so `svc/llm.py` skips the llama.cpp `_INFERENCE_LOCK` and bounds overlap with `LLM_MAX_CONCURRENT` (default 1). In local mode `get_coach_llm()` aliases the production model (no separate coach GGUF). The eval harness must be invoked as a script (`python tests/eval/run_evaluation.py`) for a cloud parity run: the hermetic `tests/conftest.py` guard pins `LLM_BACKEND=local` for the pytest suite regardless of the developer's `.env`.
* **Context**: The local-first engine shipped a single backend bound to a GPU/CPU GGUF. The Android/coach-platform delivery (ANDROID-PLAN.md) requires a hosted endpoint, but the project's identity is offline-first and its model behaviour is pinned by an empirical eval baseline (63/65 standard, 15/15 generalization) measured on the local Q4_K_M weights. A naive swap risked (a) breaking the default local path, (b) silently enabling Qwen3.5 reasoning mode and exhausting the 200-token budget, and (c) `.env` cloud settings leaking into unit tests that assert the local constructor path.
* **Rationale**: **Contained, reversible, eval-gated.** Keeping `local` the default preserves the offline product and zero-regression guarantee, while isolating cloud-specific behaviour (model IDs, thinking toggle, key handling) in one module. Fail-fast key validation converts a per-request 401 into a startup/readiness failure that operators can actually see. The `conftest.py` guard makes the suite deterministic against developer `.env` drift. The existing eval harness uses the same factories, so the local→cloud transition is gated by the same 65-case/15-case suite rather than a hand-wave.
* **Hosted trial gate (2026-09-23)**: Qwen3.5-9B passed the provider smoke, scored 62/65 standard and 15/15 generalization with the Qwen3.5-27B function-calling judge, and had no clinical-safety failures. The accepted hosted standard threshold is 62/65; the local 63/65 result remains a historical baseline.
* **Code References**: `utils/model_downloader.py` (`SafeChatOpenAI`, `CLOUD_MODEL_REGISTRY`, `DEFAULT_CLOUD_API_BASE`, `_llm_backend`, `uses_cloud_backend`, `_should_use_cloud_mock`, `_build_cloud_llm`, `get_llm`, `get_judge_llm`, `get_coach_llm`, `coach_llm`, `unload_coach_llm`), `svc/llm.py` (`_max_concurrent`, `_SEMAPHORE`, `_uses_serial_lock`, `is_coach_loaded`, `unload_all`), `tests/conftest.py`, `tests/test_cloud_backend.py`, `.env.example`, `ANDROID-PLAN.md` (Phase 0).

### ADR 013: One account for training and coaching
* **Status**: Accepted
* **Decision**: A person may train and coach through one account. Player and coach are capabilities of that account, rather than exclusive identities. This avoids duplicate accounts and training histories for coaches who also train, while requiring authorization to check the current capability and coaching assignment for each action. An account cannot assign itself as its own coach. During the closed trial, only owner-invited accounts may gain the coach capability. A person may later disable coaching, ending their assignments while retaining their own training account.

### ADR 014: Consented assignment controls training-history access
* **Status**: Accepted
* **Decision**: A coach can read a player's training history only during an active, mutually consented assignment. Before accepting an invite, the player sees the access it grants. Every invite code is single-use and acts as the coach's advance authorization for its first redeemer; the code is not tied to a named recipient, so forwarding it can change who redeems it. The player must explicitly accept before immediate binding. Codes expire quickly, the coach receives an in-app and email notice on redemption, and the coach may immediately revoke the assignment. The email contains no training data. Revocation ends access to both current and earlier history. This avoids recipient verification for invites while limiting each code to one assignment.

### ADR 015: Durable account identity and deletion
* **Status**: Accepted
* **Decision**: Each account has an immutable identity distinct from its reusable username. JWT subjects identify the immutable account, while current capabilities and the session epoch are checked in the durable registry before any ledger is opened; a missing or deleted account fails closed. Account deletion invalidates sessions there, removes the live ledger and user-specific backup copies, and prevents an old token or restored backup from recreating the deleted identity. A former username may be registered again only as a new account. Fly volume snapshots are disabled; restricted whole-catalog recovery backups may retain deleted rows for up to 30 days, as disclosed to users. Every restore reapplies a durable deletion record kept outside the restored snapshot. This separates identity and revocation from the ledger being deleted while preserving username reuse and bounded disaster recovery.

### ADR 016: Minimize data sent to hosted models
* **Status**: Accepted
* **Decision**: The closed trial discloses hosted AI processing before use. Player inference receives the user's message and only the context needed to answer it; coach inference receives only the selected player's necessary telemetry, without account names or contact details, and never receives player-assistant chat. Coach-assistant exchanges are kept in memory for one selected player and are cleared on player switch, revocation, logout, or app close; the service does not persist a coach-assistant transcript in the trial. This permits hosted inference for the Android service while limiting unnecessary disclosure and cross-player context. User-written free text may still contain identifying information and must be described honestly in the privacy notice.

### ADR 017: Flutter is the product client
* **Status**: Superseded in part by ADR 022 for closed-trial client scope
* **Decision**: MAYOS is migrating to a mobile application, beginning with Android only for the closed trial. The Flutter app is the product client, backed by the FastAPI service; the Streamlit interface is legacy migration reference and serves no users. Delete it after the four-week trial passes its exit gates and opted-in real-user imports finish, before public launch. The local GGUF backend remains available for development and evaluation. This concentrates delivery and design work on one user experience while retaining useful engine test paths.

### ADR 018: Coach applies substitutions to coach-controlled programs
* **Status**: Accepted
* **Decision**: After a coach publishes a player's program, the player requests an exercise substitution and the coach applies any replacement. Existing player-side substitution paths must become requests for coach-controlled programs; the coach owns the resulting program change. A request can be applied, declined with a short player-visible reason, or cancelled. Recording a skipped or unplanned exercise truthfully in a workout is allowed and does not change the program; the coach sees that divergence while assigned. This preserves the coach's responsibility for the program without falsifying the player's workout history. Self-service remains available before coach publication and after assignment revocation.

### ADR 019: Opt-in import of existing training history
* **Status**: Accepted
* **Decision**: The mobile service does not bulk-import every local ledger. Existing real users may explicitly opt into an audited import of their histories, receive new immutable account IDs, and complete a secure account-claim path. Local ledgers include development and test data, mixed schema versions, and mostly lack password credentials, so automatic import would risk creating unwanted or insecure cloud accounts. The import uses consistent SQLite snapshots and verifies record counts before cutover.

### ADR 020: Offline workout drafts with idempotent sync
* **Status**: Accepted
* **Decision**: The Android player may capture workout drafts without connectivity and sync them when connected. Chat and program changes remain online. Each draft carries a stable client session ID, performed date and timezone, and the program version used while logging; server commit must be idempotent so retries cannot create duplicate workouts. If a coach publishes a newer program before sync, the workout remains a historical record against the captured version and does not change the new program; both parties see the version difference. Unsynced drafts survive app restart and logout in protected storage isolated to that account, with a logout warning and explicit discard action. Account deletion erases drafts on the deleting device; another offline device erases them when it next checks account status. Performed dates may be entered or corrected up to three days back, while upload/edit timestamps remain available for audit and affected absence alerts are recalculated. This adds a sync contract to the current online-only workout endpoint because workout logging is a core mobile task even when connectivity is interrupted.

### ADR 021: Structured, resumable mobile onboarding
* **Status**: Accepted design; implementation pending
* **Decision**: The Android onboarding flow will collect named answers on focused screens and save each completed answer to the account. Players may resume and edit earlier answers before confirming first-program creation. Available values in incomplete three-step intakes will prefill the new flow; missing values will be requested. The existing program generation rules, including the required male/female specialization choice and the coaching-only use of body proportions, remain in effect. Hosted-processing disclosure remains before any onboarding answer leaves the device.
* **Rationale**: The current text-only, three-step intake response cannot reliably restore or revise individual screen answers. A structured contract adds API work, but gives the mobile flow explicit validation, recoverable progress, and a migration path for trial accounts without changing program behavior.

### ADR 022: One web app joins Android in the closed trial
* **Status**: Accepted client scope; web technology pending feasibility
* **Decision**: The free closed trial requires the Android Flutter app and one web app serving both player and coach capabilities through the same FastAPI service. The iPhone player web experience covers the Android trial features while online; Android alone supports offline workout drafts. Web and Android share behavior, data, privacy boundaries, and the MAYOS design system while adapting layouts to phone and desktop. The trial coach web experience includes the roster, assigned-player history, programs, requests, and alerts. Streamlit remains unused legacy software. Extending Flutter to web is the first candidate, contingent on browser authentication, routing, Safari, responsive-layout, and failed-write verification. If a Flutter-specific limitation blocks the required experience, use another web frontend against the same API. Hold the trial if the browser still cannot support the required online behavior. * **Rationale**: Trial coaches need a desktop workspace and iPhone players need access before public launch. One capability-aware web app avoids splitting account and assignment behavior across two web products; keeping web online-only avoids promising Android's offline-draft guarantees in a browser.

### ADR 025: Coach drill-down history is catalog-gated per assignment
* **Status**: Accepted
* **Decision**: A coach's roster remains catalog-only: `GET /coach/assignments` lists active assignment identities without opening any player ledger. Each drill-down read (summary, volume/sessions, exercises, exercise history, personal records) is keyed by `assignment_id` and resolves an active assignment owned by the authenticated coach in the catalog *before* mounting the player's ledger. Because the gate reads the live catalog, revocation ends access to both current and earlier history immediately, and no player-assistant chat is ever part of a coach response.

Excluding chats from the read surface honors the disclosure boundary in ADR 016.

### ADR 026: Assignment-gated coach program publication
* **Status**: Accepted
* **Decision**: An assigned coach publishes a player's program through `POST /coach/assignments/{assignment_id}/program` (optional `user_split_override`, `rep_preference_override`, `frequency_override`). The route resolves an active assignment owned by the authenticated coach in the catalog *before* mounting the player's ledger (ADR 025); an unknown, ended, or foreign assignment denies identically. The generated program is stamped with the publishing coach's account id as provenance and a stable integer `version`, persisted in the player ledger (schema v5→v6 adds `version` and `published_by_coach_account_id`; the migration backfills existing rows sequentially by `created_at`, keeping NULL provenance). Publication activates the program immediately. Program authority follows the CONTEXT.md "Program authority" glossary: the player keeps self-service until the first coach publication, then the assigned coach owns program structure. Every player write path — self-service generation (`POST /programs/generate`), active-program auto-generation (`GET /programs/active`), onboarding completion, profile-triggered rebuild, the assistant's program-mutation node, and the assistant's substitution node — obeys the single `player_controls_program` decision and is refused only while the *active* assignment's coach is the active program's publisher, with the same "Your assigned coach controls your program. Ask your coach for changes." message. Unassignment retains the program's content and provenance and returns authority to the player automatically. The player receives a catalog in-app notice (`kind: program_published`) surfaced via `GET /assignments/notices`, with `POST /assignments/notices/read` marking them read.
* **Context**: Players needed a coach's prescription to become their live program, but the data lives in a per-user ledger while assignment consent lives in the shared catalog, and program provenance must survive unassignment. A naive gate would either let a route open a ledger before authorization or let the player silently overwrite a coach's prescription while still assigned.
* **Rationale**: **Gate first, then record.** Keying publication to the assignment id keeps the authorization decision in the catalog and the ledger mount strictly behind it (ADR 025), so revocation ends control on the next call with no extra state. Storing provenance and a monotonic version on the program itself — rather than in the assignment — makes the prescription durable across unassignment and gives offline drafts (ADR 020) the exact version they trained against. Checking `published_by_coach_account_id` against the active assignment's coach means authority flips back automatically the moment the assignment ends, and a fresh assignment before publication leaves self-service intact, matching ADR 018's boundary.
* **Code References**: `service/coach_programs.py` (`publish_program`), `service/programs.py` (`player_controls_program`, `COACH_CONTROLLED_ERROR`, `ensure_active_program` auto-generation gate), `service/profile.py` (`update_profile` rebuild gate), `service/onboarding.py` (`complete_onboarding` gate), `svc/routers/assignments.py` (coach publish + player notice routes), `svc/routers/programs.py` (`POST /programs/generate` and `GET /programs/active` gates), `agent/assistant_graph.py` (program-mutation and substitution node gates), `tests/test_program_authority.py`, `agent/ProgramState.py` (`GeneratedProgramSchema.version`, `published_by_coach_account_id`), `database/migration_manager.py` (`_migrate_v5_to_v6`), `mobile/lib/src/core/api_client.dart` (`coachPublishProgram`, `playerNotices`, `markPlayerNoticesRead`), `mobile/lib/src/features/coach/coach_player_history_screen.dart`, `mobile/lib/src/features/player/program/program_tab.dart`, `mobile/lib/src/features/player/assignment/player_assignment_screen.dart`.

### ADR 027: Catalog-side per-assignment program-request queue
* **Status**: Accepted
* **Decision**: A player on a coach-controlled program requests an exercise substitution or a split change through a catalog-side queue keyed by the active assignment. A request pins the exact program version, day, and slot with the desired replacement or split parameters and a reason, and never changes the program on creation. The coach resolves it through assignment-gated routes: apply claims pending→applied atomically (preventing a double-apply or a racing cancel from both succeeding) before writing a NEW immutable program version that preserves the coach's provenance, while decline claims pending→declined and carries a short player-visible response. A stale target — program version changed, day/slot gone, or the player regained self-service — is revalidated against the active program and refused with a clear error while the request is left pending. Players can cancel their own pending requests. The coach receives generic in-app and email notices with no training detail in the email; both clients surface request state.
* **Context**: Players needed a way to ask for program changes after a coach takes ownership (ADR 018/026), but the program lives in a per-user ledger while assignment consent lives in the shared catalog. Mutating the program in place on request would either let a player edit a coach's prescription or race a concurrent publication, and an error that names the missing condition would leak program state.
* **Rationale**: **Pinned target, atomic claim, immutable write.** Storing the queue in the catalog keeps resolution behind the same gate-first authorization as the rest of the coach surface (ADR 025), so revocation ends control on the next call. Pinning the version/day/slot makes the request unambiguous and lets apply revalidate before any write, while the pending→resolved claim runs first so two resolvers cannot both win. Writing a new immutable version instead of editing the referenced one keeps the requested version truthful for offline drafts (ADR 020) and preserves `published_by_coach_account_id`. Truth-in-workout logging (ADR 018) still stands: a request is the only program-changing path while the coach owns the program.
* **Code References**: `database/database_manager.py` (`create_program_request`, `get_program_request`, `resolve_program_request`, `list_program_requests_for_player`, `list_program_requests_for_assignment`), `service/program_requests.py` (`create_request`, `apply_request`, `decline_request`, `cancel_request`, `_notify_coach`, `_notify_player`), `service/email_sender.py` (`send_program_request_email`), `svc/routers/assignments.py` (player create/list/cancel + coach list/apply/decline), `svc/schemas.py` (`PlayerProgramRequestIn`, `ProgramRequestOut`, `PlayerProgramRequestListOut`, `CoachProgramRequestListOut`, `ProgramRequestDeclineIn`), `tests/test_program_requests.py`, `mobile/lib/src/core/models.dart` (`ProgramRequest`), `mobile/lib/src/core/api_client.dart` (`playerProgramRequests`, `createPlayerProgramRequest`, `cancelPlayerProgramRequest`, `coachProgramRequests`, `applyCoachProgramRequest`, `declineCoachProgramRequest`), `mobile/lib/src/features/player/assignment/player_assignment_screen.dart`, `mobile/lib/src/features/coach/coach_player_history_screen.dart`.

### ADR 028: Workout divergences are factual history
* **Status**: Accepted
* **Decision**: A workout divergence is a factual record of how the performed session differed from the day's prescription: a prescribed exercise the player skipped (`kind: 'skipped'`) or a working exercise the player performed that the prescription did not call for (`kind: 'unplanned'`). Divergences live in the ledger as `session_divergences` rows keyed by session, each carrying the exercise id, resolved exercise name, kind, and creation time. They are recorded at commit (`service/workouts.py` `commit_session`) by comparing the day prescription against the performed working sets, and are never a program change: recording a divergence does not alter the training program, its provenance, or authority. The same facts surface identically on the player logger (the commit response and `get_latest_session_summary` history reads; the mobile logger surface arrives with the offline-workout capture ticket, #34) and on the assigned coach's drill-down behind the existing catalog assignment gate (`service/coach_history.py`), so a former or unrelated coach sees nothing.
* **Context**: Logging truth-in-workout sessions (ADR 018) allows the player to train differently from the prescription, but the prescription and the performance disagreed silently, leaving the player and coach unable to see what was actually done. The program must remain the coach's authority (ADR 026) while the performed history stays truthful, and the extra facts must not leak to coaches who no longer hold the assignment.
* **Rationale**: **Record the difference, never rewrite the plan.** Storing divergences as immutable ledger rows beside the session keeps performed history separate from prescribed structure, so reading them can never mutate the program or its provenance, and the gate-first coach surface (ADR 025) continues to decide who may read them. Computing at commit — when both the prescription and the working sets are known — makes the comparison a one-time factual derivation rather than a replayed query, while an empty batch writes nothing so ordinary matching sessions carry no noise. Keying each surface to the same rows means the player and the assigned coach see exactly the same truth, and assignment scoping keeps that truth private to the active relationship.
* **Code References**: `database/database_manager.py` (`session_divergences`, `record_session_divergences`, `list_session_divergences`, `list_divergences_by_session`, `get_latest_session_summary`), `database/migration_manager.py` (`_migrate_v6_to_v7`), `service/workouts.py` (`commit_session`), `service/coach_history.py`, `svc/schemas.py` (`CoachPlayerDivergenceOut`), `tests/test_workout_divergences.py`.

### ADR 029: Expected training schedule and prospective pauses are player-owned ledger facts
* **Status**: Accepted
* **Decision**: A player sets the weekdays they expect to train and their IANA timezone, and may schedule a future pause, through `GET/PUT /profile/schedule` and `GET/POST /profile/schedule/pauses`. A schedule edit appends a new effective-dated version (`training_schedules`, schema v7→v8) and never rewrites an earlier one, so `get_schedule_effective_on(trainee_id, date)` resolves the weekdays that were expected then — attendance for a past date is read against the then-effective schedule. The schedule is deliberately separate from the program's `weekly_frequency` and ordered training days: setting it never generates, rebuilds, reorders, or republishes a program, and never changes day order. A pause is prospective (`starts_on` today or later), lasts at most 14 days, has `starts_on <= ends_on`, carries no reason field, and is stored as a `training_pauses` ledger row; overlaps are allowed and attendance only needs coverage. The assigned coach sees the current expected weekdays + timezone and the upcoming/active pauses (`ends_on >= today`) on the existing drill-down (`service/coach_history.py::player_summary`) riding the existing assignment gate, with no new authorization. Writing a pause also writes a best-effort in-app coach notice (`kind: training_pause`) keyed to the active assignment via `get_active_assignment_for_player`; the notice failure never fails the pause, and with no active assignment no notice is written while the pause still succeeds.
* **Context**: Players needed to declare when they actually expect to train, independently of how a program happens to order its days, and to signal planned time away. Rewriting schedule history would retroactively change what was expected of earlier dates, and letting a pause mutate the program would let a player edit a coach's prescription (ADR 018/026). Pauses also need to reach the coach without widening the coaching data-access surface.
* **Rationale**: **Append facts, never rewrite expectations.** Storing effective-dated schedule versions as immutable ledger rows keeps every past expectation truthful and makes attendance comparison a lookup against the schedule effective on that date, not the latest one. Keeping the schedule out of the program preserves program authority (ADR 026) and the single `player_controls_program` decision, so a player can describe their week without touching the prescription. Reusing the assignment-gated drill-down for visibility — rather than a new coach endpoint — keeps revocation immediate and authorization in one place (ADR 025), while the best-effort notice mirrors the existing program-request pattern; a pause remains a fact the player owns and the coach merely observes.
* **Code References**: `database/database_manager.py` (`training_schedules`, `training_pauses`, `append_training_schedule`, `get_schedule_effective_on`, `list_training_schedules`, `schedule_training_pause`, `list_training_pauses`, `list_active_or_upcoming_training_pauses`), `database/migration_manager.py` (`_migrate_v7_to_v8`), `service/schedule.py` (`local_today`, `current_schedule`, `get_schedule`, `set_schedule`, `schedule_pause`, `get_pauses`, `_notify_coach`), `service/coach_history.py` (`player_summary`, `_schedule_and_pauses`), `svc/routers/profile.py` (schedule and pause routes), `svc/schemas.py` (`TrainingScheduleOut`, `TrainingScheduleUpdateIn`, `TrainingScheduleSetOut`, `TrainingScheduleVersionOut`, `ScheduledPauseOut`, `TrainingPauseIn`, `TrainingPauseListOut`, `TrainingPauseCreateOut`, `CoachPlayerScheduleOut`, `CoachPlayerPauseOut`), `tests/test_training_schedule.py`.

### ADR 030: Missed expected-day alerts are catalog-side and evaluated deterministically
* **Status**: Accepted
* **Decision**: An assigned coach is alerted when a player misses two consecutive expected training days. A pure module, `service/attendance.py`, evaluates attendance with no database access from five inputs: the effective-dated schedule versions (ISO weekdays 1=Mon..7=Sun, timezone, `effective_from`), the player's pauses (`starts_on..ends_on` inclusive), one local performed date per committed session (`workout_sessions.session_date`, duplicates preserved), the evaluation window start (the player's local date of the assignment's `started_at`, floored to the first schedule version's `effective_from`), and the current instant. The player's local day is derived in the one ADR 029 place (`service/schedule.py`: `timezone_for_versions`, `local_date_in`). An *expected day* is a local date in the window whose ISO weekday is in the schedule version effective on that date and that no pause covers. It is *due* once local now reaches the start of the local date two days later (the end of the day plus a 24-hour local grace period); a day not yet due is neither satisfied nor missed. Iterating performed dates oldest-first, each performed date satisfies at most one expected day — the earliest not-yet-satisfied expected day `e` with `e <= performed_date <= e + 1` — so two workouts on one local day satisfy two expected days, each expected day is satisfied by at most one workout, and leftover workouts satisfy nothing. A *missed expected day* is due and unsatisfied. The trailing missed run is measured over expected days: a satisfied expected day breaks it whether or not that day is due yet, while an unsatisfied day not yet due neither counts as missed nor breaks the run, so satisfying an expected day auto-resolves the alert immediately. The catalog-side `coach_alerts` table stores each alert with `UNIQUE(assignment_id, kind, dedupe_key)` (the missed-day dedupe key is the streak's start date; the shape and migration are generalised in ADR 031), and a `roster_attendance` summary row (`assignment_id` PK, `current_missed_streak`, `last_evaluated_at`, `timezone`) is updated by evaluation. `service/missed_day_alerts.py::evaluate_assignment` opens the player's ledger, runs the pure evaluation, and then: for a trailing streak of length ≥ 2 it inserts one `new` alert for that streak (insert-or-ignore) and a best-effort coach in-app notice (`kind: missed_expected_days`, message carrying the missed date range and no training detail), extends the same alert's `details` (`last_missed_date`/`missed_count`) for longer streaks, auto-resolves any open (`new`/`acknowledged`) alert whose streak is no longer current with `resolved_by='system'`, and updates the roster summary. `run_sweep` evaluates every active assignment, skipping (and counting) a player whose ledger does not exist and logging one player's failure without stopping the sweep; it unbinds the player's ledger from the worker thread after each evaluation. The session-commit hook (`service/workouts.py`, using the caller's verified account id and the player's local today for the performed date) best-effort re-evaluates the player's assignment after the workout is committed, then unbinds. An in-process loop in `svc/app.py` lifespan runs `run_sweep` once at startup and every `MAYOS_ALERT_SWEEP_INTERVAL_SECONDS` (default 3600; `0` disables), skipped under `SKIP_LLM_LOAD=true`. The coach alert centre is catalog-only: `GET /coach/alerts` (default new + acknowledged), `POST /coach/alerts/{id}/acknowledge` (new → acknowledged, idempotent; a resolved alert stays resolved), and `POST /coach/alerts/{id}/resolve` (new/acknowledged → resolved with `resolved_by='coach'`, idempotent). `GET /coach/assignments` entries gain `alerts_new`, `alerts_acknowledged`, and `current_missed_streak` read only from catalog tables.
* **Context**: A player's schedule and pauses live in the per-user ledger while alert state must be readable by the coach's roster and alert centre without mounting a ledger (ADR 025/029). Attendance has to be deterministic and timezone-correct across grace boundaries, and a repeated or concurrent sweep must not fire duplicate alerts or resurrect a resolved one.
* **Rationale**: **Pure evaluation, catalog transitions, idempotent sweep.** Keeping the date arithmetic in a DB-free module makes the grace, timezone, pause, version, and one-workout-per-day rules testable in isolation, with the ADR 029 helper as the single definition of the player's local day. Storing alerts and the roster summary catalog-side keeps the coach surface gate-first and ledger-free (ADR 025), while the `(assignment, kind, dedupe_key)` unique key plus insert-or-ignore makes retries and concurrent sweeps safe. Resolving a different streak and never touching a resolved alert means "acknowledged" and "resolved" remain durable coach decisions, and the hourly in-process cadence is safe because evaluation is idempotent and due-ness is per player-local day. The best-effort commit hook mirrors the existing notice pattern: attendance is refreshed when a workout lands, but a failure never fails the workout commit.
* **Code References**: `service/attendance.py` (`evaluate_attendance`, `version_effective_on`), `service/schedule.py` (`timezone_for_versions`, `local_date_in`, `local_today`), `service/missed_day_alerts.py` (`evaluate_assignment`, `evaluate_for_ledger`, `run_sweep`, `list_alerts`, `acknowledge_alert`, `resolve_alert`), `service/workouts.py` (`commit_session`, `_evaluate_missed_days`), `database/database_manager.py` (`coach_alerts`, `roster_attendance`, `insert_coach_alert`, `get_coach_alert`, `list_coach_alerts`, `update_coach_alert_details`, `acknowledge_coach_alert`, `resolve_coach_alert`, `resolve_open_coach_alerts_for_assignment`, `upsert_roster_attendance`, `get_roster_alert_badges`, `list_all_active_assignments`, `list_performed_dates`, `unmount_user`), `service/assignments.py` (`list_coach_assignments`), `svc/routers/alerts.py`, `svc/schemas.py` (`CoachAlertOut`, `CoachAlertListOut`, `CoachRosterEntryOut`), `svc/app.py` (`_alert_sweep_loop`, `lifespan`), `scripts/run_alert_sweep.py`, `tests/test_attendance.py`, `tests/test_missed_day_alerts.py`, `tests/test_coach_alerts_api.py`, `mobile/lib/src/features/coach/coach_alerts_screen.dart`, `mobile/lib/src/features/coach/coach_assignments_screen.dart`, `mobile/lib/src/core/api_client.dart` (`coachAlerts`, `acknowledgeCoachAlert`, `resolveCoachAlert`), `mobile/lib/src/core/models.dart` (`CoachAlert`, `CoachRosterEntry`), `mobile/test/coach_alerts_test.dart`.

### ADR 031: Check-ins are immutable facts and follow-ups use a weekly cadence
* **Status**: Accepted
* **Decision**: A check-in is a catalog-side immutable fact recorded by an assigned coach through `POST /coach/assignments/{assignment_id}/check-ins`, carrying a strict `YYYY-MM-DD` `checked_in_on`, a `channel` from the fixed set `in_app`/`in_person`/`phone`/`video`/`message`/`email`/`other`, and an optional trimmed note of at most 500 characters (empty becomes `NULL`). The date may not be in the player's local future and may not predate the assignment's local start date. Both bounds use the timezone cached on `roster_attendance` by the missed-day sweep when it exists; until it is cached each bound takes the most permissive local day on earth rather than UTC, so an unknown-timezone player is never falsely rejected. The future-date (upper) bound uses the latest possible local day, `Pacific/Kiritimati` UTC+14, so a player ahead of UTC is never told their own today is in the future. The assignment-start (lower) bound uses the earliest possible local day, `Etc/GMT+12` UTC-12, so a check-in dated on the assignment's real start day is not rejected as predating it once UTC+14 has already rolled into the next calendar day; a cached timezone applies to both bounds. The follow-up `due_on` computation is separate and keeps its ADR 029 behaviour: it uses the cached timezone, falling back to UTC (never the permissive bounds). Every coach read and write rides the existing ADR 025 catalog gate, so an unknown, ended, or other-coach assignment returns the same generic denial; the rows themselves are keyed by player account id, so `GET /assignments/me/check-ins` returns the player's complete history across active and ended assignments, including the former coach's username, while the former coach loses access the moment the assignment ends. Check-ins are never edited or deleted. The weekly follow-up cadence is one constant, `FOLLOW_UP_CADENCE_DAYS = 7`: the next due date is `(latest check-in checked_in_on for the assignment, else the assignment's local start date) + 7 days`, and an alert is due when the player's local today reaches it. Follow-up evaluation (`evaluate_follow_up`) is catalog-only and is the single place that transitions follow-up alerts: it runs in the coordinated hourly sweep and immediately after a check-in is recorded. It computes `due_on`, resolves with `resolved_by='system'` every open (`new`/`acknowledged`) follow-up alert whose dedupe key differs from `due_on` or whose follow-up is no longer due, and then, if due, insert-or-ignores the alert for `due_on`; the dedupe key is the due date, so repeated or concurrent sweeps never duplicate it. Recording a check-in only writes the fact and re-runs this evaluation, so a backdated check-in that does not move `due_on` (dated at or before the latest check-in) leaves an overdue alert open, while a check-in that moves `due_on` resolves the old alert. A coach acknowledge/resolve works unchanged for this kind; a manually resolved alert stays silenced until `due_on` moves, because the next check-in produces a new dedupe key and the resolved row is never reopened. Coach in-app notice on creation mirrors ADR 030's best-effort pattern. `coach_alerts` is generalised from its missed-day-only columns (`streak_start_date`, `last_missed_date`, `missed_count`, `UNIQUE(assignment_id, kind, streak_start_date)`) to `alert_id, assignment_id, coach_account_id, player_account_id, kind, dedupe_key, details` (JSON, kind-specific), `state, created_at, acknowledged_at, resolved_at, resolved_by` with `UNIQUE(assignment_id, kind, dedupe_key)`; the missed-day kind keeps `dedupe_key = streak_start_date` and `details = {streak_start_date, last_missed_date, missed_count}`, and the follow-up kind uses `dedupe_key = due_on` and `details = {due_on, last_check_in_on}`. Existing catalogs are migrated in place with the standard SQLite table rebuild inside one transaction (create the new table, copy rows mapping the old columns into `dedupe_key`/`details`, drop, rename, recreate indexes), detected via `PRAGMA table_info` and idempotent on a second init. `roster_attendance` gains an additive `timezone` column written by the missed-day evaluation, and each roster entry gains `next_follow_up_on` computed from catalog tables only. The alert API response keeps the common fields and flattens the kind-specific `details` beside them (`kind`, `streak_start_date`/`last_missed_date`/`missed_count`, `due_on`/`last_check_in_on`), and the mobile alert centre renders either kind.
* **Context**: Coaches need to record contact that happened outside MAYOS and have the coach/player history outlive the assignment, but the consent and identity live in the shared catalog while a naive implementation would either open a ledger before authorization or lose the fact when the assignment ends. Upcoming work (#33 deload/regression alerts) also needs `coach_alerts`, so the missed-day-specific shape had to be generalised once rather than widened twice.
* **Rationale**: **Record facts, gate reads, generalise idempotently.** Storing check-ins as immutable catalog rows keyed by the player account keeps the visibility rule simple: the player owns their history forever, and the coach sees it only while the ADR 025 gate resolves an active assignment, so revocation is immediate with no extra state. Making the due date the dedupe key (rather than a generated id) makes the sweep naturally idempotent and lets a new check-in's resolution and due-date shift fall out of the same computation; keeping the cadence a single constant avoids premature per-coach configuration. Generalising `coach_alerts` now, with an in-place rebuild that maps old rows into `dedupe_key`/`details`, keeps #31's behaviour and tests intact while giving #33 a ready seam, and flattening `details` into the response preserves the mobile contract without a second wire shape.

### ADR 032: Progression signals are catalog-side episodes evaluated at commit
* **Status**: Accepted
* **Decision**: Two existing progression signals become coach-facing alert events when a session is committed, reusing what `commit_session` already computed rather than adding progression maths. `deload_recommended` (subject `''`) fires when the systemic fatigue verdict (`agent/progression_engine.evaluate_systemic_fatigue`) is true after the commit. `performance_regression` (subject = exercise id) fires for an exercise whose existing summary carries `action == 'deload'` (the OVERSHOOT rule), or `projection_status == 'RPE_OVERSHOOT_DELOAD'` (a top set at RPE 10 even when the load rose, so the badge reads LOAD INCREASE), or whose e1RM fell by at least `REGRESSION_E1RM_DROP = 0.05` of the previous e1RM; an exercise without previous performance (BASELINE) never fires, even if its first top set was logged at RPE 10. The pure, DB-free `service/progression_alerts.py::signals_from_commit` derives the fired signals; `evaluate_commit` is the single transition point and uses only catalog tables plus the data passed in (no ledger reads), so the commit hook can run it after the missed-day hook has unmounted the player's ledger. A signal is an **episode**: it opens on the first committing session where it fires, stays open while later commits keep firing it, and closes on the first later commit where it does not. For the per-exercise kind, a commit that does not include the exercise leaves that exercise's episode unchanged. Episode state is tracked catalog-side in `alert_signal_state(assignment_id, kind, subject, active, episode_key, updated_at, PRIMARY KEY(assignment_id, kind, subject))`, created in `ensure_account_schema` alongside the other catalog tables. Opening an episode sets `episode_key` to the committing `session_id` and insert-or-ignores a `coach_alerts` row with `dedupe_key = '<subject>:<episode_key>'` (or just `episode_key` when the subject is empty), `details` = the signal evidence, state `'new'`, and a best-effort `service/coach_notices.py` notice that names the signal and, for regression, the exercise only. Continuing an episode updates the open alert's `details` with the latest evidence plus `latest_session_id`/`latest_session_date` and never creates a second alert. Closing an episode resolves its open (`'new'`/`'acknowledged'`) alert with `resolved_by='system'`. A coach-resolved alert whose episode is still active stays resolved; a new alert only appears after the episode closes and a later commit re-opens one. Re-processing the same session is a no-op: the whole evaluation for one commit runs in a single catalog transaction (`DatabaseManager.catalog_transaction`, also used by the coach-alert shape rebuild) and, inside it, writes a `progression_alert_sessions(assignment_id, session_id, processed_at, PRIMARY KEY(assignment_id, session_id))` marker; `evaluate_commit` returns a no-op when `(assignment, session)` is already marked, so replaying an older session after later ones cannot duplicate an alert, overwrite its evidence, or close a newer episode. Catalog write methods detect the active transaction and defer their own commit, so a failure anywhere rolls the whole evaluation back and the next retry applies it cleanly; coach notices are sent only after the transaction commits. The extend path looks the open alert up by `(assignment, kind, dedupe_key)` and never inserts, so only an episode open creates an alert. Evaluation happens only at commit (no sweep work for these kinds); the hook runs only when an `account_id` is supplied and the player has an active assignment, and any failure is logged and never fails the commit. The kinds ride the existing catalog-gated `GET /coach/alerts`, acknowledge/resolve endpoints, and roster badge counts (ADR 025/030/031), so only the active assigned coach sees them; `present_alert` flattens their evidence into the response and `CoachAlertOut` declares the new fields.
* **Context**: The coach needed deterministic deload and regression visibility, but the progression facts are computed inside the player's ledger at commit while alert state must be read catalog-side without mounting a ledger, and a naive per-commit alert would duplicate on retries and drown the coach in repeated notifications. The missed-day and follow-up kinds had already generalised `coach_alerts` (ADR 031) precisely so this ticket could reuse it.
* **Rationale**: **Reuse the signal, episode the alert.** Deriving the signals from data `commit_session` already produced keeps a single definition of "deload" and "regression" and avoids a second progression engine. Making a signal an episode (rather than a per-commit event) matches how a real regression persists across sessions and gives one durable alert per occurrence, while the `(assignment, kind, dedupe_key)` unique key and the catalog-side `episode_key` make the transition idempotent under retries. Keeping the evaluator catalog-only and calling it after the missed-day hook means revocation and reassignment keep working through the existing gate with no new authorization and no ledger mounted during the request beyond what the hook already does. The 5% threshold is one named constant so the one heuristic in the path is tunable in a single place.

### ADR 033: Offline workout capture syncs idempotently into one ledger transaction
* **Status**: Superseded in part by ADR 034 and ADR 035
* **Decision**: A player may capture a workout as a protected draft on the device (online or offline) and sync it once connectivity returns. Each draft carries a stable client-generated `client_session_id` (UUID, generated once and never changed), the performed date and IANA timezone, the captured program `version`, the capture instant, the day order, sets, readiness, and notes. `POST /workouts/sessions` is extended, not replaced: when `client_session_id` is absent the legacy online-only behaviour is unchanged; when present, `performed_date` (strict `YYYY-MM-DD`), `performed_timezone` (validated IANA), `program_version`, and `captured_at` (timezone-aware ISO instant) are required. The performed date may not be later than the player's local today in `performed_timezone` and may not be more than three days before the local date of `captured_at` in that timezone (ADR 020); `captured_at` may not be in the future beyond a 10-minute clock-skew tolerance; an unknown timezone is refused 400 rather than guessed. `session_date` is the performed date. The ledger schema v8→v9 adds nullable `client_session_id` (partial UNIQUE index where not null), `performed_timezone`, `program_version`, `captured_at`, and `uploaded_at` to `workout_sessions`, plus `session_commits(client_session_id PRIMARY KEY, session_id, response_json, committed_at)`. All ledger writes for one commit — the session row, its sets, divergences, personal records, debrief, chat pointer, and the `session_commits` idempotency row — run in one caller-managed ledger transaction (a re-entrant `ledger_transaction()` with write helpers that defer their commit; PR writes commit through `_commit_ledger()`). If a commit for `client_session_id` already exists, the exact stored response is replayed (HTTP 200; the first commit is 201) and nothing is written; concurrent duplicates are serialised by `BEGIN IMMEDIATE` plus the unique index, with the loser replaying the winner's response. A mid-commit failure rolls the whole commit back, leaving no session, sets, or commit row, and a later retry succeeds. When `program_version` differs from the player's active program version the request is refused 409 `{"error": "program_version_mismatch", "active_version": N}` and writes nothing (ticket #35 will accept older versions as history). `GET /workouts/sessions/by-client-id/{client_session_id}` returns the stored response (200) or 404, so the client reconciles a lost response before retrying. Post-commit catalog hooks (missed-day evaluation and progression alerts, ADR 030/032) run only after the ledger transaction commits, stay best-effort, and are safe to re-run. On the device, drafts live in `flutter_secure_storage` under `drafts.<account_id>` (account-separated, keystore-backed) and the active program plus per-day prescription are cached per account for offline logging; logout warns and offers explicit keep/discard, and discard requires an explicit choice. A Riverpod `DraftSyncService` processes the logged-in account's pending drafts oldest-first: it first calls the status lookup (200 → synced with that response), else POSTs the draft (200/201 → synced, with the response kept); network/timeout/5xx stays pending for a later retry; 409 or another 4xx becomes `needs_reconciliation` with the server message and no auto-retry, and the player can retry or discard. It is triggered on app start/login, right after a draft is saved, by a manual "Sync now", and on a 60-second foreground timer. The drafts list shows Pending / Synced / Needs attention with the server message and retry/discard actions; synced drafts are retained for display (pruned after 24 hours).
* **Context**: Mobile workout logging is a core task even when connectivity is interrupted, but the ledger is per-user and connection-scoped, so a draft must be captured without the service and later committed exactly once. Naively retrying an online endpoint would create duplicate sessions whenever a response was lost, and writing a session, its sets, divergences, PRs, debrief, and chat pointer as separate commits would leave partial workouts on a crash or mid-commit failure. The prescription is needed offline, and unsynced drafts must survive logout without leaking between accounts.
* **Rationale**: **One idempotency record, one transaction.** Making the client session id the idempotency key and storing the exact response makes retries and lost-response reconciliation trivial and safe, while the unique index plus a single write transaction makes concurrent duplicates impossible without a coordination service. Refactoring ledger write helpers to defer to a caller-managed transaction (mirroring the catalog-side pattern from ADR 032) keeps one atomic unit without duplicating SQL. Validating dates against the player's own performed timezone and capture instant, rather than the server clock, keeps near-midnight and far-from-UTC workouts truthful (ADR 029/030). A mismatch with the active program is refused with 409 at this stage: it never silently rewrites the active program, and the client surfaces it as an explicit needs-attention state. Ticket #35 (ADR 034) later narrows that refusal: an older captured version that still exists in the ledger commits as history, while a newer or unknown version keeps the 409. Protected, account-namespaced secure storage with an explicit logout keep/discard choice honours ADR 020's offline-draft guarantee without surprising data loss.

### ADR 034: Offline drafts captured against an older program commit as history
* **Status**: Accepted
* **Decision**: A draft captured against the player's current program commits against that version; a draft captured against an **older** version that still exists in the player's ledger commits as a historical session against the exact day plan it trained against. The newer active program is never modified, reactivated, or rewritten, and the stored session keeps its captured `program_version`. Version resolution happens inside the same ledger transaction as the commit (after `BEGIN IMMEDIATE`): an equal version resolves to the active program, an older version resolves through a ledger lookup by version (`get_program_by_version`, sharing the active program's loader), and the day is taken from the resolved program. Refusal rule: a captured version that is **newer** than the active version, or **absent** from the ledger (no stored program row has it), is still refused with 409 `program_version_mismatch` and nothing is written; an active program without a version also refuses any captured version. The v9→v10 migration adds nullable `active_program_version_at_sync` to `workout_sessions`, populated only for offline-sync commits (the active version at the moment the draft synced); legacy and online-only sessions keep it NULL. The commit response and the player and assigned-coach reads expose `program_version`, `active_program_version_at_sync`, and a derived `is_historical_program` flag. Post-commit hooks (missed-day attendance and progression alerts) and PR detection run for historical sessions too, because the workout is real performed history: attendance must count it and progression must see it. Idempotent replay is unchanged: an existing `client_session_id` still replays its exact stored response before any program or catalog validation. The active coach's read remains behind the ADR 025 catalog assignment gate, so a coach revoked before the sync cannot read it.
* **Context**: Offline drafts can be captured just before a coach publishes a newer program and synced after (ADR 020/033). Refusing them as a 409 loses real training history the player already performed, while naively accepting them risks either committing against the wrong prescription or letting a stale draft rewrite the coach's newer program. The version a draft trained against is a stable integer already stored on each program row and on the session itself (ADR 026), so the exact historical prescription is still recoverable from the ledger.
* **Rationale**: **Resolve the captured version, never the current one.** Loading the day plan from the exact program row the draft recorded keeps performed history truthful and leaves the active program immutable, so program authority (ADR 026) is untouched. Resolving inside the commit transaction keeps the concurrent-publication check from racing an earlier read, and reusing one program loader means the historical path can never diverge from the active path. Persisting the active version at sync for offline-sync commits (rather than recomputing "current" on every read) makes the shown version difference a historical fact rather than a moving target; online-only sessions have no captured version and keep the column NULL. Running the normal hooks honours the fact that the session really happened, matching the missed-day and progression-alert rules (ADR 030/032); the only edge is that a backdated session's PR is compared against the ledger's running max, which is already the PR definition (ADR 009). The gate-first coach read (ADR 025) already denies a revoked coach because it reads the live catalog before mounting the ledger, so no new authorization code is needed.

### ADR 035: Recent performed dates can be corrected within the entry window
* **Status**: Accepted
* **Decision**: A player corrects a recent committed session's performed date through `PATCH /workouts/sessions/{session_id}/performed-date` with `{"performed_date": "YYYY-MM-DD"}`. The route is player-authenticated and operates on the caller's own mounted ledger only, so an unknown or another player's session id is a plain 404 that reveals nothing. The performed date is validated by one shared, **capture-anchored** window helper (`service/workouts.py::_performed_date_window`) used by BOTH offline entry (`validate_sync_fields`, ADR 033, now tightened) and correction (`validate_performed_date_correction`): `capture_local_date - MAX_BACKDATE_DAYS <= performed_date <= min(capture_local_date, player_local_today)`. A performed date can therefore never be after the capture's local date (nor in the player's future) and never more than three days before it; local dates come from the ADR 029 `local_date_in` helper. The capture instant is `captured_at`, else `uploaded_at`, else `started_at` for a legacy online session; the timezone is the session's `performed_timezone`, else the player's current schedule timezone (`latest_schedule_timezone`), else UTC. Correction is refused 409 when the session is older than the window (its capture local date is more than `MAX_BACKDATE_DAYS` before the player's local today), so long-past history cannot be rewritten. Correcting a session to its **own current date** is an idempotent no-op checked first — before the recency/window validation, after the 404 ownership check and date-format parse — returning `changed: false` with no correction row and no `edited_at` change, so an old session corrected to itself stays unchanged rather than 409. Otherwise the session read AND all validation run inside the same `BEGIN IMMEDIATE` `ledger_transaction()` that writes the change (mirroring ADR 034's resolve-inside-the-transaction rationale, so the date cannot be corrected against a session that changed under a concurrent commit): `session_date` is rewritten, `edited_at` is stamped, and an immutable `performed_date_corrections(id, session_id, previous_date, corrected_date, corrected_at)` row is appended; `uploaded_at` and `captured_at` are never touched. Error codes: 404 unknown/foreign session, 400 malformed/post-capture/out-of-window date, 409 session too old to correct. The idempotent sync record (`session_commits.response_json`) is immutable and replays the original stored response on `POST /workouts/sessions`; the current-state read `GET /workouts/sessions/by-client-id/{client_session_id}` overlays, via `service/workouts.py::session_state`, the live session's `session_date`, `edited_at`, and `corrections` (the same key the coach responses use). The `performed_date_corrections` DDL lives in one place (`migration_manager.PERFORMED_DATE_CORRECTIONS_DDL`) shared by the fresh-create path and the v10->v11 migration. After a successful correction only the missed-day attendance evaluation re-runs, best-effort and after the transaction exits (`_evaluate_missed_days` -> `evaluate_for_ledger`), so a correction that fills a missed expected day resolves the open alert with `resolved_by = 'system'` and a correction that removes a satisfying workout can open or extend one; progression alerts and PR detection are intentionally not recomputed. The ledger v10->v11 migration adds nullable `workout_sessions.edited_at` and the cascading `performed_date_corrections` table. The active coach sees `uploaded_at`, `edited_at`, and the correction history on the existing ADR 025 gate-first summary; a revoked coach sees nothing. The player client derives the same capture-anchored window (`mobile/lib/src/core/performed_date_window.dart`), edits an unsynced draft's date locally within it, offers "Correct date" on a synced workout (requires connectivity; surfaces a clear offline/refusal error), and adopts the server's `session_date` on sync/reconcile and after a correction.
* **Context**: ADR 020 promised that performed dates may be entered or corrected up to three days back and that affected absence alerts are recalculated, but #34 only shipped the entry half; a player who mistyped or mis-set the date had no way to fix recent history, and the coach saw the wrong day. Correction must not become an unbounded rewrite of training history, must not falsify audit timestamps, and must not make a stored idempotent response mutable.
* **Rationale**: **Reuse the window, keep the ledger honest.** Validating against the same capture-anchored window as entry means "correctable" and "enterable" are the same rule in one place, and the post-capture ceiling stops a draft or correction from inventing a later workout than was actually captured; the separate recency check stops an old workout from being silently rewritten. Checking the no-op before the window means an old session can still be confirmed at its own date without a spurious 409. Reading the session and validating inside the write transaction closes the TOCTOU window a concurrent commit could otherwise open. Making the correction an immutable append-only row (with the session's `edited_at` as the pointer) preserves both the original date and every change for the coach and for audit, while leaving `uploaded_at`/`captured_at` untouched. Keeping `session_commits` immutable but overlaying the corrected date on the by-client-id read separates the idempotency guarantee from the display truth, so a retry can never double-commit yet the client still shows the corrected date; the client likewise adopts the server date on reconcile. Re-running only the missed-day hook reflects the one derived fact a date change can alter — attendance — and avoids falsely re-firing or clearing progression episodes whose evidence did not change; the best-effort pattern keeps a hook failure from failing the correction. The correction appends facts rather than mutating program or assignment state, so the existing gate-first coach read continues to decide who may see it. Keeping the DDL in one shared constant means the fresh-create schema and the migration cannot drift.

### ADR 036: Hosted player chat is disclosed, streamed, and online-only
* **Status**: Accepted
* **Decision**: The Flutter player client ships a hosted assistant chat screen (`mobile/lib/src/features/player/chat/chat_screen.dart`) over the existing service surface: `GET /chat/history`, `DELETE /chat/history`, and the SSE `POST /chat/messages` (`data: {"token"}` chunks, a final `data: {"done": true, "response_content", "program_updated"}`, and `event: error` frames). A transport-free `SseDecoder` (`mobile/lib/src/core/sse.dart`) decodes the wire format; it normalises CRLF across chunk boundaries (a trailing `\r` is held back until the next chunk), tolerates arbitrary chunk splits, and exposes `close()` to flush a final frame that arrived without a trailing blank line; the byte stream is decoded with the chunked `utf8.decoder` so a multibyte character split across chunks is reassembled. `streamChatMessage` converts any failure while the stream is open — a dropped connection, or a non-2xx body such as a 429 from `CHAT_LIMIT` (whose JSON `detail` is surfaced verbatim) — into an `ApiException` (network failures have a null status code). Tokens are appended to a live draft as they arrive; only the `done` frame finalizes and caches the reply. An `event: error` frame, a transport failure mid-stream, or a turn that ends without a `done` frame shows a clear error state and never persists a partial reply as finished. The screen holds its stream subscription and cancels it on dispose; secure-storage reads at start-up are best-effort. A `done` frame with `program_updated: true` refreshes the cached active program so the Program tab and workout logger see the change. History can be cleared with a confirmation dialog (`DELETE`); logout clears the account's cached history (history lives server-side, so nothing is lost) while disclosure acceptance stays per account. The offline banner carries a Retry that reloads history and clears the offline state, and a successful send clears it too. Before the first chat use the app shows a short, honest hosted-processing disclosure (the player's message and the needed training context go to a hosted model provider; free text may contain identifying information, per ADR 016) that must be accepted before the composer is enabled; acceptance is persisted per immutable account id in `SecureChatCacheStore` (`chat_disclosure.<account>`), so a new account sees it again. The last-loaded chat history is cached per account (`chat_history.<account>`) for read-only offline viewing. `GET /chat/history` annotates every message with `kind` — `debrief` for the session-logged pointer, else `message` — using the one shared predicate `agent/chat_markers.py` (`is_session_pointer_text`), which `agent/assistant_graph.py` also uses to trim the pointer from model context; the client renders the debrief card from `kind` and never re-derives it from the wording. `service/chat.py::prepare_user_turn` makes a failed-turn retry idempotent: when the most recent stored message is a `user` message with identical content and no assistant reply after it, the turn runs against the existing history instead of inserting a second user row; the mobile client, on any send failure, reloads the server history (so the persisted user message shows once) and Retry re-sends the same content without adding another local bubble. Chat send and every server-side program-changing action the player app has today — program regenerate (`program_tab.dart`), program-request create/cancel (`player_assignment_screen.dart`), and profile/schedule/pause edits (`profile_screen.dart`) — require connectivity and are never queued: a transport failure shows one shared line, `needsConnectionMessage` (`"This needs a connection. Nothing was changed."`) from `mobile/lib/src/core/connectivity_message.dart`, while a server refusal keeps its own `detail`. Detection reuses the app's existing signal (`ApiException.statusCode == null`, matching `DraftSyncService`); no connectivity package is added. `DateStorage`-style duplication was removed by extracting one shared keystore helper, `mobile/lib/src/core/secure_store.dart` (`SecureStore`), used by both `workout_storage.dart` and `chat_storage.dart`.
* **Context**: ADR 016 promised a hosted-processing disclosure before use and that player inference receives the user's message plus only the needed context, while coach inference never receives player-assistant chat; ADR 020/022 promised that chat and program changes stay online while cached reads remain offline. #37 is the client half of that promise on the Android player (chat + debrief with a clear disclosure and private history). Building it needed a decision about how the SSE stream is parsed and surfaced, where the disclosure and read-only history live on device, and how "needs connection" is signalled without promising offline chat.
* **Rationale**: **Stream in, finalize once, keep it private.** Parsing the incremental SSE frames (rather than waiting for the whole body) lets the reply render live while the server-side `done` frame stays the single source of truth for the persisted, scrubbed message, so a dropped connection can never leave a half-written reply in local history; making any mid-stream failure an `ApiException` lets the screen's offline/refusal handling work uniformly. Holding back a trailing `\r` and using a chunked UTF-8 decoder keeps the decoder correct at arbitrary network boundaries rather than at message boundaries. Persisting disclosure acceptance and cached history by immutable account id reuses the ADR 020 account-namespacing already proven for drafts, so another account on the same device is never shown the wrong consent or the wrong conversation, and a failed online read still leaves the last-loaded history readable. Clearing only the cached history on logout (not acceptance) keeps a private conversation off a shared device without re-prompting the same account. One shared connectivity string and signal keeps a single definition of "offline" across drafts and chat and avoids a new dependency. Labelling the commit pointer server-side (`kind`) keeps one predicate shared with the prompt builder, so the writer and the detector cannot drift and the client never pattern-matches emoji. Making the retried turn idempotent server-side keeps the ledger truthful — a failed turn's user message is real and must not duplicate — and reloading it client-side means the retry shows exactly one bubble. Rendering the commit pointer as a debrief card rather than a chat bubble keeps the debrief visible without pretending it was an assistant answer, and refreshing only the program after a `program_updated` turn honours ADR 026's program authority by re-reading the authoritative program instead of mutating anything locally. The model input already excludes account identity (the telemetry header carries training facts, not the username or recovery email; `custom_instructions` and `preferred_name` are intentional user-authored context, per ADR 016), and every coach-facing read is catalog-gated or ledger-scoped without touching `chat_history` (ADR 025); `tests/test_player_chat_privacy.py` pins both by capturing the real model payload and enumerating every coach route from the app's route table. The coach program-generation path is deterministic (blueprints, no model call), so it cannot carry chat.

### ADR 037: Mobile password recovery via an Android App Link and hosted fallback

* **Status**: Accepted
* **Decision**:
  * The password-reset link is `<RESET_LINK_BASE_URL>/reset-password?token=<token>`. There is no `UI_BASE_URL` fallback — the retired Streamlit UI does not serve `/reset-password` — so unset `RESET_LINK_BASE_URL` defaults to the API's own local base `http://localhost:8000` for development only.
  * In production the host must be identical in three places: `RESET_LINK_BASE_URL`, the Android App Link intent-filter host (`-PappLinkHost`, default `mayos-api.fly.dev`), and the host serving `/.well-known/assetlinks.json` (the same API).
  * The single https URL is both an **Android App Link** when the app is installed and a **hosted fallback page** otherwise. The Android client declares an `autoVerify="true"` `<intent-filter>` for `https://<appLinkHost>/reset-password`, with `appLinkHost` injected at build time.
  * The API serves `GET /.well-known/assetlinks.json` from `ANDROID_APP_PACKAGE` (default `com.mayos.mayos_mobile`) and comma-separated `ANDROID_APP_SHA256_CERT_FINGERPRINTS`. Each fingerprint accepts upper/lower case and colons or none, is normalised to the uppercase colon-separated 32-byte form, and invalid entries are skipped with a logged warning; with no valid fingerprint the route returns **404** rather than an invalid empty statement.
  * `GET /reset-password` serves a minimal self-contained page (no external assets, per-response nonce, strict CSP, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`). Its JS reads the token from `location`, immediately scrubs it from the URL with `history.replaceState(null, '', location.pathname)`, embeds server strings via `json.dumps`, POSTs to `/auth/reset-password`, and shows a non-string-safe success/generic message; the token is never reflected into the HTML.
  * The API installs an `uvicorn.access` log filter (`svc/app.py::RedactResetTokenFilter`) that rewrites any `token=…` query value to `token=[REDACTED]`, so the token cannot reach access logs through any uvicorn CLI configuration.
  * The Flutter client uses **Flutter's built-in deep linking plus go_router** (no extra plugin): the platform route is forwarded to go_router, which matches the URL's path and reads the query token. The logged-out routes `/reset-password` (prefilled code, new + confirm password) and `/forgot-password` (email entry, constant confirmation) are public in `redirectFor` so a deep link survives the loading→unauthenticated startup resolution.
  * On a successful reset the client drops the local session and routes to login with a success message; a failure shows the service's own `detail` (falling back only when none is present), can request a new link, and a network failure uses the shared `connectivity_message.dart` helper.
  * The legacy `UI_BASE_URL/?reset_token=…` link for the retired Streamlit Recover Access tab is no longer emitted.
* **Context**: The API-side reset flow already existed (ADR 006 epoch, ADR 007 hashed single-use short-TTL tokens), but there was no way to reach it from the product client: the emailed link pointed at the legacy Streamlit UI (unused legacy, ADR 017/022), the Android manifest had only the launcher filter, and the app had no forgot/reset UI. A reset link must work for a logged-out user on a device without the app, so a pure app-scheme deep link is insufficient, and a pure web page loses the native app flow when it is installed.
* **Rationale**: **One URL, two implementations, no new client dependency.** A verified https App Link is the only mechanism that lets a single email link open the app seamlessly when installed and a browser page when not, and `autoVerify` requires the association file the API serves from env — configuration, not a signed-in-app trick. A dedicated `RESET_LINK_BASE_URL` (rather than reusing the CORS origin) keeps the link pointed at the host that actually serves the reset path; the localhost default is honestly development-only. Reusing Flutter's built-in deep linking (enabled by default; `go_router` parses the full URL and matches its path) avoids a new plugin and its platform glue, and makes the behavior widget-testable by driving the same router with the full URL. Serving the hosted page from the same origin as the reset endpoint means no CORS and no token in a third party's logs; a nonce-based CSP keeps the inline style/script strict while the page stays self-contained, `history.replaceState` keeps the token out of browser history, `json.dumps` keeps server strings from breaking the script, and a 404 for an unconfigured association file avoids caching an invalid statement that would fail verification. The access-log filter covers every deployment regardless of uvicorn flags. Making the recovery pages public in the router — including during the startup auth resolution — is what lets a deep link actually land instead of being bounced to login. The client clears the local session on success because the reset bumps the server epoch (ADR 006), so the stored bearer is already dead. **The local `TestClient` round trip (`tests/test_mobile_password_recovery.py`) is automated; the deployed round trip (AC3) is verified by the manual checklist in `docs/DEPLOYMENT.md` §10.8, which has not been run yet.**

### ADR 038: Hosted-model usage is metered per account and capped before inference

* **Status**: Accepted
* **Decision**: During the closed trial every hosted-model call is metered catalog-side by the **immutable account id** and model, and each account's live inference paths are rate-limited before any model call starts.
  * **Metering hook.** A LangChain callback (`utils/model_metering.MeteringCallback`) is attached to every model the downloader builds (`utils/model_downloader._build_cloud_llm`, and the local production/judge GGUF loads), so `invoke`, `with_structured_output`, and `stream` all meter themselves without touching the call sites. The cloud model sets `stream_usage=True` (OpenAI `stream_options.include_usage`) so streamed turns report real tokens rather than the fallback. The callback writes one `model_usage` row per **model call**: `id, account_id, role ('player'|'coach'|…), model, purpose, input_tokens, output_tokens, estimated, cost_usd, created_at`, indexed on `(account_id, created_at)` and `(created_at)`. `utils` never imports the service layer: `svc.app` registers the sink once at startup (`utils.model_metering.set_recorder(service.model_metering.record_model_usage)`), and the unregistered default is a no-op that logs once at DEBUG.
  * **Attribution.** `svc.llm`'s entry points (`inference_slot`, `run_inference_sync`, `bound_stream`, `run_inference`) take one `InferenceScope(account_id, role, purpose, admit)` and set a contextvar around the whole turn; callers pass the verified account from the route (`account_id_of`). A call with no context (startup, eval scripts) is recorded **unattributed** (`account_id NULL`) rather than dropped, so total spend stays complete; live request paths always attribute.
  * **Missing usage.** When a provider returns no usage metadata the callback falls back to a documented chars/4 estimate and flags the row `estimated=1`; a per-model price table (`MODEL_PRICING_JSON`, USD per 1M tokens, defaults for the configured models) converts tokens to `cost_usd`. An unknown hosted model meters at cost 0 with one logged warning; local GGUF ids (`local:*`) are intentionally cost 0 and never warn.
  * **Per-account limits.** `service/model_limits.admit_model_request` enforces `MODEL_RATE_LIMIT_REQUESTS` (per account per minute, default 20) and `MODEL_DAILY_TOKEN_LIMIT` (per account per UTC day, default 200,000) keyed by immutable account id, before the gate is taken. The window count, day-to-date token SUM, and append run in **one critical section**, so concurrent turns for one account cannot all pass at L-1. The daily token cap is a **soft cap**: it is checked at admission from tokens already recorded, and a turn's tokens land when its calls end, so an in-flight turn can overshoot by at most one turn. One **user turn** counts as one request (a chat turn that makes several model calls still counts once), while all of its calls and tokens are metered. The per-turn guard is keyed by account id and held with a context reset token that is released when the scope exits, so a later turn is enforced again. Exceeding a limit raises `ModelLimitExceeded`; a single `svc.app` exception handler returns HTTP **429** with a clear JSON `detail` for every route. The streamed chat route pre-admits before starting the SSE stream (so streaming cannot bypass the limit) and passes `admit=False` to its `bound_stream`; onboarding, program generation, and coach publication ride the same admission.
  * **Owner alert.** `service/model_metering` computes month-to-date actual spend and projects the full month as `actual / max(elapsed_fraction, 0.1)`, where the elapsed fraction is over the UTC calendar month and the `0.1` floor (≈3 days) prevents a day-1 blow-up. When the projection reaches `MODEL_SPEND_ALERT_USD` (default 50) the alert is evaluated **only on the existing hourly alert sweep** (`service.alert_sweep.run_sweep`) — never on an inference thread while a gate slot is held — so no new loop is introduced. The UTC month is claimed once with `INSERT OR IGNORE` (`model_spend_alerts.period`); `notified_at` is set only after a successful email to `OWNER_ALERT_EMAIL`, so a failed/absent send is retried on a later sweep with a WARNING each attempt, and a delivered alert is never repeated.
  * **Owner review.** The owner reviews actual usage with `scripts/model_usage_report.py`, which opens the catalog **read-only** (`mode=ro`, never provisioning schema; a catalog without usage prints "no usage recorded yet"). It reports per account/role/model **model calls** (one row per call), input/output tokens, and cost for a date range, plus month-to-date actual and projected totals and the current month's alert status (fired/notified). Requests are counted per **model call** here while the rate limit counts **turns**, which the script documents. This is the same operator-CLI mechanism as the coach-invite and alert-sweep scripts; players/coaches never see usage beyond their own 429 message.
* **Context**: Hosted inference during the closed trial has real per-token cost, but `svc/rate_limit.py` keys by IP + bearer suffix (not an immutable account) and nothing recorded tokens or cost. A single chat turn already makes several model calls, so a per-call limiter would both over-count requests and under-enforce a token budget, and a limiter placed after the stream starts could not return a clean 429. Metering had to be centralized so new call sites cannot silently escape it, and it must never be able to fail a user turn.
* **Rationale**: **Meter at the model, admit at the turn.** Attaching the callback at the model factory means every LangChain entry (`invoke`/structured/stream) is covered once, including future call sites, and `stream_usage` makes streaming report the same provider usage as buffered calls. Driving attribution through the already-existing inference entry points keeps the account identity at the authenticated boundary and gives a natural per-turn admission point; the `admit=False` seam is what lets the streamed route refuse with a plain HTTP 429 before the stream starts, which the ADR 036 client already surfaces, without double-counting. Catalog-side storage matches the existing catalog/ledger split (ADR 007/025), so the owner report and the alert read one shared table and never mount a player ledger. Claiming the alert by month before sending, and recording delivery after a successful send, makes retries and concurrent sweeps idempotent while never losing an alert; keeping the whole evaluation on the sweep thread means an SMTP timeout can never delay an inference turn. The elapsed-fraction floor is one documented constant so a spike on day 1 does not false-alarm. Keeping metering best-effort (the callback swallows every failure) and enforcing limits in one critical section express the two hard rules: observability must never break inference, and a cap must never be raceable. Registering the sink at startup (rather than letting `utils` import `service`) keeps the low-level metering module dependency-free and testable.
